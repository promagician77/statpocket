One file, committed to your repo

You asked for a small improvement that can be implemented and tested. This is it. The mechanism depends on how the app reaches Cloudflare, which I would confirm in the first ten minutes; all three versions are small.

public/_headers
/_next/static/*
  Cache-Control: public, max-age=31536000, immutable

/_next/image*
  Cache-Control: public, max-age=86400, stale-while-revalidate=604800

/api/*
  Cache-Control: no-store

/*
  Cache-Control: public, max-age=0, must-revalidate
  X-Content-Type-Options: nosniff

The last block matters as much as the first. The HTML document must keep revalidating, or a deploy would never reach anyone.

Why a one-year TTL is safe here

Every build output carries a content hash in its filename: index-B3wOnMUE.js. Change one character of source and the next build emits a different filename, and the HTML points at the new one. The old file is never requested again. That is the entire reason the immutable directive exists, which is why a long TTL on hashed assets is the standard configuration rather than an aggressive one.

How you verify it, in thirty seconds

  • Open the preview, DevTools, Network tab, Disable cache OFF.
  • Load. Then reload.
  • Today: the second load shows ~76 rows with status 304.
  • After: those rows read (disk cache) with no status code, because no request left the machine.

Plus node 09_cache_audit.js <preview-url>, which should print PASS. Nothing reaches production until you have seen it.

What this does not fix

First-time visitors still download 409 KB and parse 1.75 MB. The 745 KB CSS still blocks the first paint. The 2.8 to 5.8 second document response is untouched. Anyone telling you one header fixes your load time is overselling it. It fixes the repeat-visit half, cheaply and verifiably, which is the right first move at this size.
